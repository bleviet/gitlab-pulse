Local-first issue analytics for GitLab

Every open issue. One board.

GitLab Pulse collects the issues of your GitLab projects, maps their labels to workflow stages, and shows them as a board, a table, and charts in a dashboard that runs on your machine.

Overview

Two layouts. One board, one filter, one link.

Compact puts the board first for daily triage: a thin release rail, the summary pills, and the lanes. Analytics puts the charts above the same board for reviews. Both share the filter, and the filter and the layout are kept in the URL, so a link shows the same view.

Issue board

Every open issue, in the stage where it waits.

01 · Board

A lane per workflow stage.

Each lane header shows the stage's priority mix. Pick a priority there to filter the board; the lane stays marked. The toolbar, the page bar, and the lane headers stay pinned while you scroll, and each lane shows 10, 20, or 30 cards per page.

A table when you need the columns

The same issues as rows: title with a link to GitLab, context labels, stage, priority, days in stage, milestone, assignee, and quality hints. Ten rows per page by default, each page shown in full.

10 · 20 · 30 rows pinned header

Search

Press ⌘K and type.

The search field in the toolbar widens and takes the cursor; the board filters as you type. Every word has to appear in the title, assignee, context, milestone, priority, or stage, with a fallback to similar words when nothing matches exactly.

Press CtrlK or ⌘K anywhere on the page

Analytics

Charts that filter the board.

Click a bar, a donut slice, a day, or a quality signal: the board below shows those issues, and the other charts dim. Click it again to clear the filter. The workflow-state row stays pinned above the board, with each stage over its lane.

Releases on one rail

Milestones are coloured by health (overdue, on track, complete) around a line for today. Click one to filter the dashboard by that milestone.

Priority mix

Open and closed issues by priority. The centre selects them all.

Quality signals

Open issues without a milestone, an assignee, or a clear type.

New versus closed, per day

The last seven days. Click a day to see the issues opened or closed on it.

Local first

Your issues stay on your machine.

A collector pulls issues from the GitLab REST and GraphQL APIs, a processor applies your YAML rules and writes Parquet files, and the dashboard reads them. Nothing leaves the machine it runs on.

Three commands from GitLab to dashboard

Give the collector a GitLab URL, a token with the read_api scope, and the project IDs. Later runs fetch only issues that changed since the last one.

Connect your GitLab →
# fetch issues from the GitLab API (only what changed)
$ uv run python app/collector/orchestrator.py
# map labels to stages with your rules, write Parquet
$ uv run python app/processor/main.py
# open the dashboard on http://localhost:8501
$ uv run streamlit run app/dashboard/main.py
# or try it first with synthetic data
$ docker compose up --build

Capabilities

Built for the way your team labels issues.

0x00

Your labels, your stages

YAML rule files map GitLab labels to workflow stages, issue types, and priorities. One file per team, and a file can apply to selected projects only.

0x04

Incremental sync

The collector remembers what it fetched and pulls only issues that changed. A project that fails is logged and skipped; the others continue.

0x08

Quality hints

Issues without a milestone, without an assignee, or with conflicting type labels are counted, listed, and one click away as a filter.

0x0C

Links that keep the view

Filters, the layout, and the search are part of the URL, so a shared link opens the same view.

0x10

Synthetic demo data

Seed realistic local projects to try the dashboard without access to a GitLab instance.

Get started with GitLab Pulse.
